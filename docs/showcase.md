# YSNB OJ — 个人项目技术总结

> 面试/简历用技术总结。全文为外发版本，已脱敏：不含真实服务器地址、
> 内部路径与凭据信息。

## 一、项目定位（30 秒版）

我为校内 ACM 集训队从零自研了一套在线评测系统（OJ）：**Vue 3 前端 + Go 后端 + 完全自研的 Linux 沙箱判题机**，覆盖题库、训练题单、训练小组、ACM 赛制比赛（封榜/滚榜/组队赛）、用户出题审核流等完整业务。前后端约 1.9 万行代码，已在校内 Linux 服务器生产运行，完成了数据清理、凭据轮换、备份恢复演练和双册使用文档的交付级收尾。

做这个项目有两个动机：一是队伍确实需要一个可控的训练/比赛平台；二是我判断 OJ 里**真正有技术含量的是判题沙箱**——它逼你面对 Linux 内核的 namespace/cgroup/seccomp、进程管理、资源隔离这些业务系统碰不到的东西。所以我拒绝了「用现成开源 OJ 二开」和「接 go-judge 做壳」这两条捷径，选择判题核心完全自研。

**量化快照**：后端 13.2k 行 Go + 前端 6.1k 行 Vue/TS；判题支持 C++17/Python 3/Java 17 三语言档位 + SPJ 特判 + 交互题；压测 8 并发用户 × 8 题 64 次提交洪峰全部 AC，洪峰期间 API 延迟 ≤4ms、榜单计算 ≤6.3ms；9 套端到端测试 127 项断言全绿。

## 二、技术栈与关键选型权衡

先给速览，再逐项展开成决策记录。每条都回答四个问题：候选是什么、关键
对比维度、为什么选它、**什么情况下我会反过来选备选**——技术选型不是
站队，是约束下的排序。

### 速览

| 层 | 选型 | 主要被放弃的备选 |
|---|---|---|
| 后端 | Go 1.27 + Gin + GORM | Java/Spring Boot、Node.js |
| 数据库 | PostgreSQL（dev 用 SQLite） | MySQL |
| 队列 | Redis Stream（dev 内存实现） | Kafka/RabbitMQ、PG 轮询 |
| 通信 | gRPC 双向流 | HTTP 轮询、消息队列 |
| 实时推送 | WebSocket + 主题授权 | SSE、长轮询 |
| 前端 | Vue 3 + TS + Tailwind v4 + shadcn-vue + TipTap | React + AntD |
| 沙箱 | 自研（cgroup v2 + ns + seccomp） | go-judge、isolate、Docker |
| 会话 | JWT + 封禁点查 | 纯服务端会话 |
| 部署 | 单机 systemd 裸机 | Docker Compose、K8s |

### 2.1 后端语言：Go，而不是 Java / Node.js

判题机的日常工作是**进程管控**：fork/exec、namespaces、cgroup、seccomp、
信号处理、看门狗——全是贴近 syscall 的活。三个候选对比：

- **Java/Spring Boot**：业务生态最厚，但判题核心要么走 JNI 调 libc（开发
  痛苦、部署带原生依赖），要么起子进程包一层 C 工具（多一层 IPC 和故障
  面）；JVM 本身吃内存，判题机常驻进程轻不了。此外「Windows 开发机一条
  命令交叉编译出 Linux 单静态二进制」这个日常体验，只有 Go 原生给得起
  ——这个项目从开发到部署的全部迭代速度都建立在这上面。
- **Node.js**：异步模型对 IO 密集的 API 层够用，但精细控制进程树生命周期
  （杀 PID1 收全树、lease 续期、多任务并发闸）时，弱类型 + 回调风格在
  这种状态机代码里出错成本高。
- **Go**：goroutine 的并发模型刚好匹配「一台判题机同时判 N 道题、每道题
  一棵受控进程树」的形态；`golang.org/x/sys` 对内核接口的封装完整；团队
  也有储备。

**什么时候我会反过来选**：如果这个系统的重心是企业业务流程（审批流、
复杂权限编排）而非判题，Spring 的生态收益会压过一切，我会选 Java。

### 2.2 数据库：PostgreSQL，而不是 MySQL

判题与比赛场景的关键需求是**事务正确性 + 复合唯一约束兜底并发**：报名
去重靠 `(contest_id, user_id)` 复合唯一索引，组队赛整队报名靠单事务写
全员行、任一冲突整体回滚。PG 的约束违反分类、事务隔离行为在这类用法
上更省心；JSON 类字段（标签、样例）两边都存 text，但 PG 后续想升级
JSONB 查询（比如按标签索引）路径更顺。MySQL 完全能做，但在我最依赖的
两个点（约束语义、复杂查询）上 PG 的心智负担更小，没有选 MySQL 的理由。

开发态用 SQLite 而不是本地起 PG：GORM 抽象层让双方言共用一份 schema，
本地零依赖跑通全部业务逻辑，只有判题调度和并发行为需要到真环境验证——
这层切换在 E2E 直打生产时自然覆盖。

### 2.3 判题队列：Redis Stream，而不是 Kafka / RabbitMQ / PG 轮询

队列要的语义：任务不丢（consumer group + pending 重投）、可观测（队列
长度进监控页）、低延迟。逐个排除：

- **PG 轮询/`SELECT FOR UPDATE SKIP LOCKED`**：少一个组件，但队列长度、
  消费延迟、积压告警都要自己造，且判题峰值和业务查询共库互相干扰。
- **Kafka**：为校内规模的单机判题引入 Kafka，运维成本（ZK/KRaft、分区
  规划）远超问题规模——这是「简历驱动架构」的典型反面。
- **RabbitMQ**：语义合适，但和 Redis 二选一时，系统本来就需要 Redis 做
  限流与会话，Stream 顺手就有了，少一个中间件。

Redis Stream + consumer group 提供了 ack/pending 语义；再往上自己包一层
租约（15 分钟 lease + 断线重排 + 孤儿扫描）保证判题机崩溃也不丢任务。
队列接口抽象成 `internal/queue`，开发环境换内存实现，零依赖。

**什么时候我会反过来选**：多校联用、判题机集群到几十台、需要回放历史
任务流时，Kafka 的日志保留与分区吞吐才真正开始值钱。

### 2.4 API ↔ 判题机：gRPC 双向流，而不是 HTTP 轮询 / 消息队列

判题机和 API 之间是一条**长会话**：注册、心跳（带负载遥测）、任务下发、
结果回传、数据拉取授权，全都发生在同一条连接上。三种形态对比：

- **HTTP 轮询**：实现最简单，但任务下发延迟 = 轮询间隔，心跳和结果回传
  要各自造端点，判题机数量一多轮询风暴先到。
- **消息队列**：把「会话」拆成两条队列，状态同步（判题机在线状态、容量
  变化）反而没有自然的位置放。
- **gRPC 双向流**：一条流承载全部消息类型（proto 里一个 `Connect` 就够），
  判题机**主动外连**——意味着判题机不开任何入站端口、加一台判题机只是
  多一个出站连接，水平扩展不需要动防火墙和负载均衡。强类型 proto 也让
  「任务里带什么字段」在编译期锁死。

### 2.5 实时推送：WebSocket + 主题授权，而不是 SSE / 长轮询

需求是**双向**的：客户端订阅（我要看提交 123 的结果、比赛 5 的榜单），
服务端定向推送，且订阅本身要过权限（提交详情只有本人可看、admin 主题
只有管理员可订）。SSE 是单向的，订阅请求得另走 HTTP，授权状态要跨两个
通道维护；长轮询在「榜单 + 多提交」多主题场景下连接数和延迟都不可接受。
WebSocket + 连接内主题订阅模型让「鉴权一次、按主题授权多次」成为自然
结构（细节见 5.1）。**什么时候反过来选**：如果只需要服务端单向推（如
通知中心），SSE 更简单，我会用 SSE。

### 2.6 前端：Vue 3 + Tailwind v4 + shadcn-vue，而不是 React + AntD

这个选型迭代过一次，两次决策各自诚实：第一版选 Element Plus 是因为团队
Vue 储备厚、出活快，且 OJ 前端是表格/表单/对话框密集的后台型应用，成熟
组件库的密度直接决定开发效率。生产跑了一段时间后做了一次全量重构，换到
**Tailwind CSS v4 + shadcn-vue（reka-ui 无头组件）**：要明暗双主题和长期
可控的视觉一致性时，无头组件 + 设计令牌比「换主题变量」的路线更彻底——
重构后 Element Plus 依赖完全移除、残留为零。两次决策都验证了同一个架构
防锁死取舍：全部 API 调用收口在 `client.ts` 一层、状态用 Pinia 隔离、
页面组件不直接依赖 UI 库的奇特行为——所以这次换 UI 库，业务逻辑层一行没动。

富文本编辑器选 TipTap 而不是「Markdown textarea + 预览」：出题人（学生
志愿者）不一定会 Markdown，所见即所得把出题门槛降了一档；TipTap 的
schema 受控模型也方便以后限制危险节点。代价是要处理它和 Vue 响应式的
集成坑（`shallowRef` 持有 editor 实例，避免深度代理和编辑器内部状态
打架——见 5.8）。

### 2.7 沙箱：自研 cgroup/ns/seccomp，而不是 go-judge / isolate / Docker

这是全项目最重要的一个「不选」，三个备选分别代表三种思路：

- **go-judge（合并自 go-judge/executorserver）**：生产验证充分、API 友好。
  但它恰恰是这个项目里最有技术含量的部分——接了它，这个项目就退化成
  「业务系统 + 别人的判题核心」，而我的目标就是吃透这一层。这不是说
  生产永远不该用成品：如果是给公司建 OJ、判题只是支撑系统，我会直接
  用 go-judge，自己写沙箱在那种场景下是负价值。
- **isolate（C 写的、ICPC 系 OJ 常用）**：代码可控可读，但 Go 主服务和
  C 工具之间多一层 IPC 协议和进程边界，故障面变宽；而且改行为（比如放
  一个系统调用、调交互题管道拓扑）要跨语言改，迭代速度掉一档。
- **Docker/containerd 当沙箱**：隔离的直观选择，但对判题场景有三个具体
  问题——每次运行起容器的延迟和资源开销对「64 提交洪峰要在几十秒内判
  完」是硬伤；镜像分发把「判题机裸机即可用」变成「判题机要维护镜像仓库
  同步」；而内核攻击面（共享内核的 namespace+seccomp）和我的自研方案
  是同一层，并没有因为用了容器就多一层内核边界。Docker 解决的是**环境
  一致性**问题，我的语言档位已经用配置驱动的 languages.yaml + 显式
  工具链清单解决了。

自研的代价是明确的：要自己面对 cgroup v2 的机器差异、seccomp 白名单的
演进、以及第三章那个 cBPF 回绕 bug。收益同样是明确的：每一层行为完全
可控可解释（出问题能 strace 到底）、零外部依赖（判题机就是单个二进制）、
以及这个项目最有含金量的技术资产。

### 2.8 会话：JWT + 封禁点查，而不是纯服务端会话

纯服务端会话（Redis session）能天然做到封禁即时生效，但每个请求都查
一次会话存储，且要多维护一个状态面。纯 JWT 无状态、验签即过，但封禁
必须等 token 过期——不可接受。取舍结果是 JWT 为主 + 每请求按主键点查
封禁标记（一次索引查询的代价买即时性），详见 5.3。这个决策的教训是
**不要把「无状态」当信仰**：无状态是手段，正确性要求（封禁即时生效）
才是约束。

### 2.9 部署：单机 systemd 裸机，而不是 Docker Compose / K8s

生产是单机：API、判题机、PG、Redis 同机。判题沙箱要直接操作 cgroup v2
和 namespace，容器化反而要处理 privileged/cgroup 挂载传递这些额外复杂
度；单机场景下 systemd 的依赖管理、自动重启、日志（journalctl）已经
覆盖需求，且排障链路最短。仓库里保留了 docker-compose 模板给「换新机
快速起环境」用，但判题机生产路径就是裸机 systemd。**什么时候反过来
选**：多机部署、判题机需要弹性伸缩时，容器化的环境一致性收益开始
超过它的复杂度成本。

### 2.10 一个贯穿性的选型原则：配置驱动优于代码分支

语言档位全在 `languages.yaml`：新语言 = 加一段配置 + 装工具链，零代码。
时限倍率（Python 4×、Java 3×）、内存放宽（JVM +512MB）、JVM 堆按题注入
（`-Xmx{MEM}m`）、是否限制虚拟地址（JVM 必须关，靠 cgroup RSS 兜底）
都是配置项。同理，沙箱白名单、资源档位、挂载策略都是数据不是散落的
if——第三章那个 seccomp bug 能被穷举测试覆盖，前提正是「白名单是一份
可以被测试消费的数据」。

## 三、核心难点 ①：自研沙箱（安全核心）

### 威胁模型

选手代码是完全不可信的输入，checker/interactor 同样不可信。目标：任凭选手代码做什么，都不能逃出单次判题的资源边界、不能读到宿主机任何其他数据、不能影响后续判题。原则是**默认拒绝、fail-closed**——漏放系统调用的后果是「某语言特性报运行错误」（可用性问题），而绝不能是安全问题。

### 方案：两段式 re-exec + 五重隔离

1. **文件系统**：在新 Mount namespace 里把 `/` bind 重挂为只读（NOSUID/NODEV），`/proc` `/sys` 换成全新只读实例，`/tmp` `/dev` `/dev/shm` 换成有上限的 tmpfs，`/home` `/root` `/var` 用空 tmpfs 盖死——整个沙箱只有本任务工作区一个可写点。
2. **身份**：挂载完成后 `setresuid` 降权到 nobody（65534）再 exec 用户程序。
3. **资源**：cgroup v2 封顶 memory（禁 swap）/cpu/pids；RLIMIT 封输出体积、栈、CPU 秒级兜底；wall-clock 看门狗到点**杀 PID1**——用户程序就是 init，杀掉它整个进程树随之回收。
4. **系统调用**：seccomp cBPF 白名单，白名单外一律 SIGKILL。
5. **网络**：新 Network namespace，无任何接口，物理上断网。

实现上是「两段式」：父进程 clone 出新 namespaces 后 **re-exec 自身二进制**，子进程读环境变量里的任务规格完成挂载、降权，最后一步才装 seccomp 并 execve 目标程序。有个容易踩的细节：PATH 解析必须在装 seccomp **之前**做——现代 glibc 的 stat 走 `newfstatat`，装完过滤再解析工具路径会把自己杀死。

### 一次真实的内核层 Debug（我最有含金量的复盘）

上线 Java 档位后，所有提交编译期就失败：运行错误、**stderr 完全为空**、22ms 死亡。排查路径：

1. 先怀疑环境：服务器没装 JDK？装了 OpenJDK 17 后手动编译同一份代码成功——排除环境。
2. 对比沙箱内外：`runuser nobody` 手动编译也成功——排除权限/属主。
3. **strace 挂到判题进程**，复现一次编译，直接看到 `+++ killed by SIGSYS +++`——seccomp 杀的，但第一版白名单里 stat 分明是放行的。
4. 顺着「放行了还死」这条线读到 cBPF 构造代码：每条白名单项的跳转偏移是 **uint8** 算的，白名单超过 127 条后偏移**静默回绕**——合法调用落到过期的 KILL 指令上。
5. 修复：白名单重构为分块线性链（每块 ≤120 条，块间用无条件跳转蹦床衔接），任意长度安全；同时把 `newfstatat`、`clock_getres`、JVM 启动必需的 AF_UNIX socket 组补进白名单（网络 namespace 内无网卡，放行 socket 不构成出网能力）。
6. **防回归**：写了一个 cBPF 解释器测试，在判题机上穷举验证——每个白名单号必须到 ALLOW，0..459 所有非法号必须到 kill 类动作，所有跳转偏移不越界。

这个故事覆盖了面试官想看的全部：系统性排查（环境→权限→动态追踪）、内核机制的理解（cBPF 跳转语义、SIGSYS）、修复的正确性论证，以及把事故转成测试资产的习惯。

## 四、核心难点 ②：判题调度与可靠性

- **队列语义**：提交 → 校验（可见性/审核/比赛窗口/限流）→ 代码落盘 → PENDING 入队；判题机按容量拉任务，任务进入 JUDGING 并带 **15 分钟租约**。
- **容错三件套**：判题机断线，其在租约内的任务立即重回队列；后台扫描器兜底回收租约过期的孤儿任务；API 重启时启动扫描重排所有遗留 PENDING——三层保证「提交不丢」。
- **缓存**：用户编译产物按次缓存；checker/interactor 按 sha256 全局缓存编译一次；测试数据按 sha256 增量拉取——压测中 64 次提交在 2 并行判题下随提交即判完，靠的就是编译缓存。
- **交互题**：选手程序与 interactor **各自进沙箱**、由父进程搭桥双向管道，任一方退出立即终止另一方；interactor 独立 30s 看门狗。防死锁是设计出来的，不是跑出来的。

## 五、核心难点 ③：前后端之间的工程问题（重点）

这一章是我认为 OJ 区别于普通 CRUD 项目的部分——前后端的契约要同时服务「实时性、正确性、防作弊、安全」四个目标。

### 5.1 判题状态实时性：WebSocket 的鉴权与授权设计

**问题**：判题结果要实时推给选手（否则提交后只能轮询）。**约束**：浏览器发起 WebSocket 握手时**无法设置 Authorization 头**——这不是实现细节而是协议现实，标准的 JWT 中间件在 WS 路由上永远 401。
**方案**：WS 升级走 `?token=` 查询串做独立鉴权入口（一次性校验后进入长连接）；连接内按**主题**授权——`submission:<id>` 只有本人/相关者订阅有意义，`contest:<id>` 给比赛页榜单用，`admin:*` 基础设施主题在连接内再做角色校验，防止普通用户订阅判题机监控。
**效果**：判题结果、榜单更新零轮询实时到达；主题模型让「谁有权看什么」在连接层就收口。

### 5.2 榜单一致性与封榜：服务端算好再广播

**问题**：ACM 榜单 = 解题数/罚时/封榜/打星/作弊标记的复合计算，前端各算各的必然出现选手之间榜单不一致。**方案**：榜单计算完全在服务端（含冻结区间折叠——封榜后的提交对未解出的题显示 `?n`，不泄露任何结果信息），以事件广播增量刷新 + 定期全量校正；**组队赛**在服务端把个人行折叠成队伍行（任一队员 AC 即队伍 AC 取最早时间、错误尝试合并计罚），前端拿到的就是最终形态。**效果**：所有观众看到的榜单字节级一致，封榜不泄露，组队赛零前端聚合逻辑。

### 5.3 JWT 无状态 vs 封禁即时生效的矛盾

**问题**：JWT 的优点是无状态，但封禁账号必须**立即**生效——token 还有几小时有效期，等它过期等于没封。**权衡**：全量改服务端会话（Redis session）放弃 JWT 无状态性，代价不值；完全信任 token 则封禁形同虚设。**方案**：保留 JWT，但加一层每请求中间件按用户主键点查封禁标记——一次主键查询的代价换取封禁的即时性，高权限操作另有角色校验。**效果**：封禁秒级生效且已登录会话同步失效。

### 5.4 大文件上传的安全面

**问题**：测试数据以 zip 上传（上限 128MB），zip 是经典的攻击面（炸弹、路径穿越、内存耗尽）。**方案**：全局请求体上限；上传先**流式落盘临时文件**（不进内存）→ zip 目录解析后逐条目按限额读取 → 文件名走正则白名单提取纯数字序号，**统一重编号为 1..N**，zip 内的原始路径完全不落盘 → 无有效输入的整包拒绝。导入外部题目包（DOMjudge/Hydro）沿用同一套管道并额外解析元数据。**效果**：上传面收敛为「大小受限、路径不可控、内存不可炸」。

### 5.5 权限模型：前后端双保险 + 越权链设计

**问题**：OJ 的角色边界是安全边界（admin 能改密码、封人）。**方案**：后端四级角色（user/setter/admin/super_admin）+ 后台接口三层分组（staff 只读/admin 管理/super 授予权限），**admin 的授予与收回只能由 super_admin 操作**——斩断「一个 admin 自己造 admin」的越权链；审核流、题目可见性、比赛裁判权全部在后端判权。前端路由 meta 做角色 gate、按钮做条件渲染——但明确这是体验层，真正的门都在后端。**效果**：越权尝试在后端 403，前端只是不给你看入口。

### 5.6 比赛题独立副本：一个数据模型决策

**问题**：比赛题目若直接引用题库，赛中改题会污染正在进行的比赛。**方案**：比赛挂题时复制题目与测试数据为**独立副本**，赛中改原题不回灌；副本的可见性绕过公开标记、由「比赛是否已开始」控制——比赛前看不到题面、开赛即见、赛后自动转补题。这个决策同时解决了「补题开放」的语义：同一份代码提交时按上下文决定是否计入榜单。

### 5.7 并发正确性：让数据库兜底

典型例子是比赛报名：前端防重复点击不可靠，接口层先查后插有竞态——最终用**复合唯一索引**兜底（同比赛同用户只能有一行），冲突时给业务化的提示（「请先取消原报名」）；组队赛整队报名在一个事务里写全员行，任一成员已单独报名则整队回滚。原则：**并发正确性放在约束层，不放在「先查一下」的侥幸里**。

### 5.8 契约纪律与渲染安全

- 错误响应统一 `{error}` 结构，前端单一收口函数转用户提示，后端 binding 校验（表单必填/长度）与前端校验双份但**以后端为准**。
- 题面/题解是用户可控的富文本：渲染层 `html:false`（markdown-it 原始 HTML 直接转义）+ 代码高亮对语言白名单 + KaTeX 渲染数学，从源头避免存储型 XSS；编辑器用 TipTap 受控回填（`shallowRef` 持有 editor 实例避免 Vue 响应式代理与 TipTap 内部状态冲突——这是集成富文本库的真实坑）。
- 时间统一 UTC 存储按本地展示；判题机与 API 间传输限制元数据+哈希，二进制数据走带鉴权的专用端点且路径参数全数字校验（防路径穿越）。
